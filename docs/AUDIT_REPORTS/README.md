ORBIS AUDIT REPORTS

Project: ORBIS Foundation
Directory: "docs/AUDIT_REPORTS/"
Purpose: Permanent chronological record of ORBIS implementation and verification activity.

---

1. PURPOSE

This directory stores implementation audit reports.

Audits may be created for work performed by:

- Gemini
- OpenAI/ChatGPT
- Human developers
- Other AI systems
- External implementation partners

The audit history is part of the ORBIS engineering record.

---

2. FILE NAMING

Every audit uses:

NNN_YYYY-MM-DD.md

Examples:

001_2026-08-13.md
002_2026-08-13.md
003_2026-08-14.md

The number is sequential.

The date represents the creation date.

---

3. SERIAL NUMBER

Do not manually guess the next number.

Use:

./scripts/new-audit.sh

The script finds the highest existing audit number and creates the next number.

---

4. REQUIRED INFORMATION

Each audit should contain:

- Audit ID
- Date
- Time
- Implementer
- Task
- Objective
- Scope
- Files added
- Files modified
- Files removed
- Architecture impact
- Database impact
- Security impact
- Tests
- Build verification
- SonarCloud result where applicable
- Git branch
- Git commit SHA
- Problems found
- Fixes applied
- Remaining issues
- Risks
- Final status

---

5. STATUS VALUES

Allowed status values:

- "PLANNED"
- "IN_PROGRESS"
- "PASS"
- "PASS_WITH_NOTES"
- "REVIEW_REQUIRED"
- "FAILED"
- "BLOCKED"

A report must not be marked "PASS" without verification.

---

6. AUDIT PRINCIPLE

Audit reports must record what actually happened.

Do not hide:

- Failed tests
- Build failures
- Security concerns
- Architecture deviations
- Unresolved issues
- Temporary workarounds

8. AI IMPLEMENTATION RULE

Before implementation, an AI developer should:

1. Read "docs/00_PROJECT_INDEX.md".
2. Read relevant architecture documentation.
3. Read the latest relevant audit reports.
4. Define the implementation scope.
5. Implement only the approved scope.
6. Run verification.
7. Create/update the audit report.
8. Commit the work.
9. Push to GitHub.

---

9. PROHIBITED PRACTICES

AI developers must not:

- Redesign architecture without approval.
- Delete existing business logic without approval.
- Introduce unnecessary dependencies.
- Claim tests passed without running them.
- Claim SonarCloud passed without evidence.
- Claim Android/root capabilities that are unavailable.
- Hide implementation failures.
- Mix unrelated modules.
- Perform destructive changes without approval.

---

10. RETENTION

Audit reports should normally never be deleted.

If a report contains an error:

- Preserve the original.
- Create a correction/addendum.
- Explain the correction.
- Preserve the historical sequence.
